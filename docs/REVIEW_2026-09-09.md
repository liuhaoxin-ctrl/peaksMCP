# peaksMCP 需求优先复评（HEAD `c4cfe62`，2026-09-09）

需求基线（不因目录结构而改变）：

> agent 通过 `search`/`get` 使用黑箱内的函数，必要时使用 peaks 的原生函数，组合这些函数处理数据；
> 以 Jupyter notebook 为人与 agent 的 context center，分为
> Contract / Access / Run / Show / Save / Observability 六个子系统，合并为一个完整 system。

## 2. 仍然断开的（按优先级）

### P0-A　`inspect_experiment` 是唯一的分类 owner，但它的返回值没有任何 Show 表示

这是本轮最尖锐的问题，而且比上一轮更集中：黑箱从 19 个收敛到 6 个之后，**6 个 adapter 里 5 个都能被 agent 看到，只有 `inspect_experiment` 是黑洞**。

| adapter | 是否 print | agent 能看到什么 |
|---|---|---|
| `load_data` | ✅ `load.py:700` | `summary_line()` |
| `convert_experiment` | ✅ `conversion.py:236` | 报告一行 |
| `plot_batch` / `plot_validation_pair` | — | "Inline figure rendered …" |
| `show_mapping_slice` | ✅ `workflows/slice_view.py` | 一行报告 |
| **`inspect_experiment`** | **❌ 无 print** | **什么都没有** |

`inspect_experiment` 返回 `ExperimentSummary`（`overrides/inspection.py:68-77`），它是 pydantic `BaseModel`，于是三条 Show 通路同时失效：

1. **stdout 通路**：不打印 → `_normalize_outputs` 没有 stdout 事件 → 返回 `[]`。
2. **repr 通路**：写 `summary.gold` 结尾 → 产出 `text/plain` → 被 `_normalize_outputs` **主动丢弃**（`tools.py:120` 注释明确说不回显 repr）。
3. **对象摘要通路**：`inspect_notebook(target="variable", …)` → `_one_line_summary`（`backend/notebook.py:194-217`）不认识 pydantic → 落到 `repr(value)[:160]`，`detail="preview"` 落到 `repr(value)[:4000]`。

而 `report_summary()`（`overrides/models.py:62-67`）对它返回 `"ok"`，`report_dict()`（`models.py:44-59`，`is_dataclass()` 判定）对它返回 `{}`——**一个字段都不剩**。

后果：manifest 承诺 `returns: ExperimentSummary (records + gold/cuts/mappings decision lists + structured conflicts)`，但 agent 执行完 `summary = inspect_experiment(scans)` 之后，既看不到 records，也看不到 gold 列表，只能去猜或者自己在 cell 里拼 `print(summary.model_dump())`——这恰恰违背了黑箱原则（agent 不该知道返回对象内部结构）。

**建议修法（三选一，推荐 1+3）**

1. 给 `ExperimentSummary` 加 `summary_line()`：`"experiment: N records (gold=[…], cuts=[…], mappings=[…]); K conflict(s)"`，`inspect_experiment` 结尾 `print` 这一行。成本最小，立刻打通 stdout 通路。
2. 在 `backend/notebook.py` 的通用对象摘要协议里加一条 pydantic 分支：识别 `model_dump`，输出有界的结构化摘要（counts + 决策列表 + conflicts，不输出完整 records）。
3. 让 Show 由契约驱动：`_normalize_outputs` 在"无 stdout、无图、但有返回值"时，不再返回 `[]`，而是返回一句提示 `"<no printed output>; call inspect_notebook(target='variable', variable_name='summary') to read the result"`。这条同时解决所有静默 facade。

### P0-B　`save_result` 是唯一持久化网关，却不在 search/get 能触达的契约里

manifest 的 `apis:` 只有 6 项，**没有 `save_result`**。`tools/search_benchmark_queries.yaml` 的注释写明了这是有意的：

> Persistence phrasing is deliberately absent: saving is the MCP-level save flow, not a searchable API.

设计意图可以理解（"不写盘，先给人看"），但它留下三个实际裂缝：

1. **agent 无法发现它**。`peaks_search_api("save")` 不会返回 `save_result`，`peaks_get_api("module:peaksMCP.overrides:save_result")` 直接 `KeyError`。
2. **在生成的代码里它会被拦**。`write_with_api_check`（`backend/notebook_unsafe.py:243-260`）对裸调用判定顺序是 builtins → 代码内定义 → 已 import → 内核 namespace → 索引精确命中，否则进 `unknown_refs` **硬阻断**。`save_result` 不在索引里、也不预注入内核 namespace，所以除非 agent 先写 `from peaksMCP.overrides import save_result`，否则 **"Execution blocked: unverifiable API reference(s) save_result"**。
3. **server_instructions 完全没提它**。`config/prompts.yaml:22` 只说 "Do not write analysis results to disk"，没说"用户要求保留时用 `save_result`"。唯一告诉 agent 这件事的是 `claude_plugin/skills/cut-preprocessing/SKILL.md:45`——一份人写的文档，不是契约。

**建议**：三选一并把选择写进契约。

* 要么把 `save_result` 作为第 7 个 adapter 写进 manifest（`side_effects` 字段正好已经在 v4 里），并加进 `server_instructions`；
* 要么明确"持久化是人的行为，agent 永不调用"，那就把 `SKILL.md:45` 和 `save.py` 的公开导出一起降级，避免 `__all__` 里留着一个 agent 用不了的名字；
* 最省事的兜底：无论如何，在 `server_instructions` 里补一句 `save_result` 的存在与用法，并把 `save_result` 加进 `_check_project_imports` 的白名单说明。

### P1-C　Observability 仍然只有"进程在哪"

`peaksMCP/observability/` 这个包里只有 `runfile.py`（121 行，写/读/校验 pid+port 的发现文件）。`security/audit.py:21` 的 `write(tool, outcome, details)` 只记录到工具调用层。

**缺的是运行台账**：`{cell_id, ts, code_hash, api_ids[], output_kind, artifacts[], save_ticket_id}`。没有它，这三类问题都答不上来：

* 这个结论是哪一个 cell、哪一批 API 产出的？
* 这张图对应的数据有没有被批准落盘、落到哪个路径、sha256 是什么？（批准本身有审计，但没有与 cell 关联）
* 一次会话下来 agent 到底动过哪些数据？

**建议**：在 `write_with_api_check` 成功返回处追加一条 `run_ledger` 事件（复用 `AuditLogger` 或独立 JSONL），把 cell id、命中的 `verified_peaks_apis`、输出种类、`save_ticket` 串起来；`peaks_get_api` 已经记录了 `verified_peaks_names`，把这条也写进去。

### P1-D　Run 的工具面没有收敛，而且仍然读不到历史

新增的 `inspect_notebook`（`tools.py:400-422`，`backend/notebook.py:282-308`）是个好设计——`target × detail` 的通用对象摘要协议，比三个专用工具干净。但它是**叠加**而不是**替换**：

```
register_safe_tools 注册 8 个：
  peaks_search_api / peaks_get_api / askuserquestion / inspect_notebook
  notebook_list_variables / notebook_read_variable
  notebook_read_active_cell / notebook_server_status
register_unsafe_tools 注册 2 个
── 合计 10 个工具
```

`inspect_notebook(target="variable")` 与 `notebook_read_variable` 功能重叠，`inspect_notebook(target="active_cell")` 与 `notebook_read_active_cell` 重叠。上一轮说的"三张名字解析网"现在变成"三种读 notebook 的方式"。

更关键的是**仍然没有 `notebook_read_context(last_n)`**：agent 只能读"当前活动 cell"，读不到 notebook 的历史。而 notebook 是这个设计的 context center——人在上面做了什么（手跑的 cell、改过的参数、留下的 markdown）对 agent 完全不可见。这是"以 notebook 为人和 agent 的 context center"这条需求里最实质的缺失。

**建议**：把 `notebook_list_variables` / `notebook_read_variable` / `notebook_read_active_cell` 从 MCP 工具面撤掉（保留为 `inspect_notebook` 的内部实现），腾出名额给 `inspect_notebook(target="history", last_n=N)`。

### P1-E　三个模块约 775 行是零引用的死代码，且最近两个 commit 还在上面修 bug

`dc71cbf` 把 `preprocess_cut` / `preprocess_mapping` / `preprocess_batch` / `fit_gold_reference` 降级为 internal。实测引用情况：

也就是说：`4f6c591`（worker 暂存、人类批准、网关发布）和 `52a0c31`（修进程池 worker 不可 pickle 的闭包）这两个 commit，**是在给一条 agent 永远走不到、也没有任何生产调用方的路径打补丁**；同时 `tests/unit/test_overrides_facades.py` 本轮 +382 行继续为它背书。

**建议**：明确二选一 —— 要么删掉这三个模块及其测试（如果"由 agent 用原生 peaks 组合"已是定论），要么承认它们是 human-in-notebook 的高层便捷 API，那就把它们写进 manifest 或至少在 `AGENTS.md` 里写清"仅人在 notebook 里用"。现在这种"不在契约、不在导出、但在维护"的状态是最差的。

### P2-G　`report_dict()` 对非 dataclass 报告丢字段

`overrides/models.py:44-59` 用 `is_dataclass()` 判定，于是：

* `ExperimentSummary` / `ConversionReport`（pydantic）→ 返回 `{}`；
* `SaveReport`（`save.py:44-65`）/ `LoadReport`（`load.py:63-74`）是**带类级默认值的普通类，不是 dataclass** → 只返回 6 个公共字段，`path` / `sha256` / `ticket_id` / `dims` 全丢。

这两个类都有 `summary_line()`，所以 Show 不受影响，`report_dict` 只是埋着的坑。建议改成 `dataclasses.asdict` / `model_dump` / `vars()` 三分支。
