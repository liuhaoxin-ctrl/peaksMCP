## P0-A · `inspect_experiment` 的结果对 agent 完全不可见 ★ 上轮 P0-A 未修

**这是当前系统最严重的问题。** 分类是整条预处理链路的起点——agent 必须先知道
哪条是 gold、哪些是 cut，才能组合后续函数。而这一步的结果，agent 一个字都看不到。

实测（`/Users/haoxin/Documents/实验数据/BP260623/data`）：

```
--- load_data 的 stdout ---
load_data: 42 file(s) indexed from data_netcdf (...); classify with inspect_experiment(scans); ...
--- inspect_experiment 之后 stdout 新增 ---
0
--- 返回值类型 --- ExperimentSummary
gold: [20]     cuts: [10, 11, 12, 15, 16, 19, 21, 22, 25, 27, 3, 5, 6, 9]
```

数据全对，但**一条 stdout 都没有**。四条路同时堵死：

1. `peaksMCP/overrides/inspection.py` 全文零 `print`、零 `summary_line`、零 `__repr__/__str__`
   （grep 全文件无命中）。`summary_line()` 只加在了 `load.py:71/383` 并在 `load.py:559/569/699` print，
   **`inspect_experiment` 没跟上**。
2. 返回值是 pydantic `ExperimentSummary`，作为 cell 末表达式产出 `text/plain`。
3. `core/tools.py:130` 注释明写 "text/plain reprs ... intentionally NOT echoed"。
4. `core/tools.py:197` 纯文本输出最终 `return []`；`stdout_lines` 也是 0（因为根本没 print）。

于是 `load_data` 热情地提示"classify with inspect_experiment(scans)"，
agent 照做，然后得到一个空回复。**这正是历史审计里"agent 退回自己解析 datasheet"的成因。**

**fix**：照 `load.py:559` 的样子给 `ExperimentSummary` 加 `summary_line()`，并在
`inspect_experiment` 返回前 `print`。一行改动，解开整条链路。
（顺带：这也是基准里 `S1_classification_visible` / `C2_blackbox_inspect` 的失败根因。）

## P0-B · NET001 判定访问不存在的属性 → cell 直接崩

`backend/notebook_unsafe.py:86-89`：

```python
requires_consent = self.state.require_consent or bool(
    scan and any(issue.id == "NET001" for issue in scan.requires_explicit_consent)
)
```

但 `SecurityIssue` 是 `@dataclass(slots=True)`，字段只有
`rule_id / description / level / line / code`（`code_scanner.py:60-68`），**没有 `id`**。

实测：

```
>>> SecurityIssue(rule_id='NET001', ...).id
AttributeError: 'SecurityIssue' object has no attribute 'id'
```

后果：`require_consent` 默认 `false`（`app/defaults/default.yaml:12`），`or` **不短路**，
右侧照样求值 → 只要某个 cell 命中了任意 `requires_explicit_consent` 规则（典型就是网络访问），
就抛 `AttributeError` 冒泡到 `_register` 的 `except Exception`，agent 收到一个内部错误，
**既没弹同意卡，也没给出可操作的提示**。而设计意图（`notebook_unsafe.py:83-85` 注释）
是"network egress (NET001) ALWAYS requires explicit user approval"——这条保证目前是死的。

注意 SAVE001/SAVE002/FILE002 在前面 `:66-78` 已被硬阻断并 raise，所以它们不会走到这里；
能走到这里的恰好是 NET001 等"本该弹同意"的规则，也就是**这条代码路径只在最需要它的时候崩**。

**fix**：改成 `issue.rule_id == "NET001"`。并补一个测试：含网络调用的 cell 在
`require_consent=false` 时应产生 consent 请求（denied/approved），而不是 AttributeError。

## P1-C · 契约 `inputs` 与真实签名不符，测试守不住

| 契约（`override_manifest.yaml`） | 真实签名 |
|---|---|
| `:96` `inputs: 'scans: LoadedScans from load_data (primary form)'` | `inspection.py:291` `def inspect_experiment(experiment, *, scans=None)` —— 首个位置参数叫 **`experiment`**，`scans` 是仅关键字的次要参数 |
| `:125` `inputs: 'items: sequence of 1D/2D ...'` | `plotting/layout.py:131` `def plot_batch(data, *, titles, max_cols=5, ...)` —— 叫 **`data`** |

风险很具体：agent 读契约后写 `inspect_experiment(scans=scans)` → 缺位置参数 `experiment` → TypeError。

而 example 用的是位置调用（`:104` `inspect_experiment(scans)`），所以测试是绿的，契约文本仍然是错的。

**fix**：把 `inputs` 从自由文本改成结构化的 `name: type` 列表，跟真实签名一起被
`inspect.signature` 校验——`signatures.py:149-157` 已经在 import 并取签名了，只差比对参数名。
（当前 `get` 只校验"能否 import 到对象"，参数名漂移不触发。）

## P1-D · 索引命名空间不规范，同一 scan 会被计两次

同一个目录里同时存在 `*.nc` 与 `*_processed.nc` 时（`data_netcdf/` 就是这种）：

```
records: 42
  10 int cut
  '10' str cut      ← 同一条 scan 出现了两次
cuts 长度: 28       ← 实际只有 14 条 cut
```

`_summarize_rows`（`inspection.py:230-278`）只是逐行 `append(index)`，不做 key 规范化，
`_as_key`（`:281-286`）也只在 `int()` 失败时回落 `str()`。
于是 `scans[10]` 与 `scans['10']` 是两个条目，`cuts` 里两者都在，
**agent 遍历 `summary.cuts` 会把每条 cut 处理两遍**。

原始 PXT 目录（`data/`）下不会触发（28 条全 int，gold=[20]、14 cuts、13 mappings，与我上一轮
独立算出的答案键一致），所以这是潜伏陷阱而非必现故障——但一旦 agent 指向含产物的目录就中招。

**fix**：三选一——① 载入时把 index 规范成单一类型；② `_summarize_rows` 按规范化 key 去重；
③ 给 `*_processed.nc` 打单独标记（它本来就不是待处理对象）。

## P1-E · 超时不中断，且 kernel 忙不忙没有工具能查

`notebook_unsafe.py:108-118` 捕获 `TimeoutError` 后返回
`{"execution_timed_out": True, "executed": False, "note": "TIMEOUT IS NOT STOP..."}`，
**不发中断**——kernel 继续跑、后续 cell 排队。`kernel_state` 由 pre/post_run_cell 维护
（`backend/base.py:75-88`），超时期间停在 `busy`，但：

- `server_status`（`backend/notebook.py:575`）**未注册为 MCP 工具**，只对外暴露 `/healthz`（`mcp_server.py:133`）。
- 所以 agent 唯一的应对是 server_instructions 里那句 "inspect the notebook first before retrying"——
  但它**查不到 kernel 是否还在忙**，`inspect_notebook` 也不报告执行状态。

`d6ff07a` 把"超时不是停止"写成了结构化提示，方向对，但没给配套的观测手段，
agent 只能靠猜。前端另有 2s settle 上限（`index.ts:15/353`），与后端 120s timeout 不是一回事。

**fix**：把 kernel busy/idle 状态暴露出来——要么注册 `server_status` 工具，要么在 `run_cell`
回复里带一个 `kernel_busy` 字段。进一步可考虑提供中断能力（否则一次失控的长计算只能重启 kernel）。

## P1-F · 无同意通道时，保存回执被标成 `denied`

`overrides/save.py:699-704`：无人可批准时回执 `status="denied"`。
但 `has_consent_channel` 因为 channel 是个函数对象而恒为 True，
于是"根本没人能批准"和"人看到了但拒绝了"在回执上**无法区分**。

这对 agent 是误导：server_instructions 明确要求
"Never claim a file was saved unless the receipt says so and the user approved the card"，
可 `denied` 会让 agent 以为人主动否了它，从而改走别路。

**fix**：区分 `blocked` / `no_consent_channel`，并在回执里给出可操作指引（"notebook 前端未连接，无法征求同意"）。

## 一条结构性提醒：Show 的"共享 context center"依赖前端在线

`inspect_notebook` 的 `cells` / `cell` target（`backend/notebook.py:489-497`）
在前端未连接时返回 `available: False, "no frontend notebook attached"`，
`_inspect_cell:542-543` 直接 `raise KeyError`；且**图像永不回传**
（`notebook.py:500/550` `cell.pop("outputs")` + `outputs_omitted: True`）。

也就是说"notebook 是人机共享 context center"这个设计目标，目前成立的前提是
**Jupyter 前端必须在线**。断连时 agent 读不到任何历史，只能盲跑。
这不是 bug（是权衡），但值得明确写进设计说明，并考虑给 `cells` target 一个
"从磁盘 .ipynb 读取"的降级路径——否则无头/自动化场景下整个 Show 层失效。
